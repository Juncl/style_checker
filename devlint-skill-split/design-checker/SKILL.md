name: design-checker
description: 基于设计规范文档的前端工程 UI 规范检查与修复能力。检查对象不限 HTML——本地任意前端工程（原生 HTML/CSS、Vue、React 等）、单文件、网页 URL 均可；规则库不限 Markdown——任意可读文本格式的 UI 校验规则均可。用户未指定时优先从会话上下文推断检查对象与规范（如上一步刚用某规范生成代码，直接说"检查一下"即可无缝衔接）；推断不出才向用户索要。本地对象：先检查是否符合设计规范并生成报告，经用户确认后在副本上逐条修复问题并复查验证；网页 URL：先采集页面 HTML 与全套 CSS，仅检查出报告（无修复）。网页采集仅为设计规范检查主线服务（领域确认、规范同步之后才采集），不提供独立的网页采集能力；采集一律用本 skill 的 --collect-web，禁止调用其他工具的网页采集。当用户提到 UI 规范检查、规范走查、检查并修复设计规范问题等场景时加载本 skill。

## 能力总览

| 命令 | 用途 | 输出 |
|------|------|------|
| `--list-specs` | 列出可用规范领域 | 领域清单表（服务端优先，本地兜底） |
| `--sync-spec <领域key>` | 检查&更新本地规范（读规范前必跑） | 「来源: server/local」 |
| `--scan-spec <领域key>` | 规范粗筛（检查必跑，替代规范通读） | 疑似规则行清单（文件 + 行号 + 原文行） |
| `--collect-web <url>` | 网页模式采集：puppeteer 拉取页面 HTML + 全套 CSS 落盘（🔴 仅为规范检查主线服务，不独立提供网页采集） | 工作目录 + page.html + css 文件清单 |
| 检查递交（数据文件） | 存档 + 生成检查报告 | 报告路径 + 工作目录 + 问题统计 |
| 修复递交（`--fix`，数据文件） | 存档 + 生成修复报告 | 报告路径 + 修复结果摘要 |

规范库 = skill 内 `specFiles/`（本地自带，唯一规范读取来源）。配套文档：`check-method.md`（检查方法论，检查前 Read）、`fix-guide.md`（修复守则，仅本地模式，用户确认修复后 Read）。

**调用方式**：`node <skill目录>/bin/design-checker.mjs <command>`。本地文件检查零外部依赖，无需 npm install；网页 URL 检查依赖 puppeteer-core + 本机 Chrome（未安装时 `--collect-web` 的 stderr 有安装指引，装好后重试）。

## 主线：检查 → 询问（仅本地）→ 修复（仅本地）→ 汇报

### 意图识别（进入主线的前置门槛）

本 skill 只做一件事：**设计规范检查（+ 本地修复）**。进入主线前先判断用户意图：

| 用户意图 | 判定 | 动作 |
|---|---|---|
| 对某对象做规范检查 / 规范走查 / 检查并修复（对象含网页 URL） | ✅ 规范检查意图 | 进入主线（网页对象 → 网页模式） |
| 只想采集 / 抓取 / 下载网页（源码、HTML、CSS），无规范检查诉求 | ❌ 非本 skill 能力 | 不跑 `--collect-web`，明确告知"本 skill 不提供独立的网页采集能力，采集仅为规范检查服务"；引导确认是否要做规范检查，是才进入主线 |
| 给了 URL 但意图不明（只说"处理一下这个网页"） | ⚠️ 模糊 | 先确认"是要对该网页做设计规范检查吗"，确认后才进入主线 |

🔴 **`--collect-web` 只能作为主线网页模式分支（下方步骤 3-a）的一环执行**——即领域 key 已确认（步骤 1）、规范已同步（步骤 2）之后。不响应"先采集存着""只采集不检查"类请求，不在主线之外单独采集。

🔴 **工具排他**：网页模式的采集一律用本 skill 的 `--collect-web`，**禁止调用其他工具的网页采集**（如 devlint-mcp 的 collect_web、ui-param-diff 的 collect-web）——他方采集产物是 DOM JSON + 截图形态，服务节点比对主线，与本 skill 的源码级检查流程和报告目录体系不配套。

### 流程

用户未提供信息且从上下文推断不出时，**不执行任何命令**，先跑 `--list-specs` 取清单，再索要：**① 检查目标**（本地工程/文件路径或网页 URL，必填）、**② 期望规范**（可选，按清单「规范名称」列展示候选，只有 1 个领域时只列 1 行）。上下文能推断（如刚用某规范生成代码后说"检查一下"）→ 简述依据直接开始，不索要。

```
用户意图：UI 规范检查 / 规范走查 / 检查并修复
  │
  ├── 1. 确认领域 key：--list-specs（🔴 禁止跨领域混用）
  │        用户已指定 → 按清单对照；未指定 → 从代码/路径推断或让用户选
  │        不在清单内 → 告知无此规范领域，检查终止
  ├── 2. --sync-spec <领域key>（🔴 读取规范前必跑）
  │        来源=local（服务不可达，静默用本地自带规范，🔴 不向用户提示）→ 继续
  ├── 3. 判断检查目标类型：http:// 或 https:// 开头 = 网页 URL，其余 = 本地路径
  │     │
  │     ├── 【网页模式】（只检查，🔴 无修复）
  │     │    a. --collect-web <url> 采集落盘（🔴 仅此环节可采集：主线步骤 1/2 已完成，
  │     │       且只采集用户要检查的那个 URL；禁止用其他工具采集）
  │     │       → stdout 返回「工作目录」+ page.html + css/js 文件清单
  │     │       → 有"跨域样式表下载失败"提示时读 manifest.json 的 failed 确认影响面
  │     │       （登录处理为通道自动闭环：无头检测到登录页/导航失败 → 自动弹出有头
  │     │         Chrome 窗口（同一持久 profile，页面顶部有"采集中请勿关闭"提示条），
  │     │         此时告知用户"请在弹出窗口完成登录，完成后自动继续"（最长等 3 分钟）；
  │     │         登录一次即沉淀到本地，后续采集免登。
  │     │         "等待用户操作超时"报错 → 让用户重新发起检查。
  │     │         ⚠ bash 调用超时设 ≥ 5 分钟，避免有头登录等待被掐断）
  │     │    b. Read 工作目录下 page.html + css/*.css 为检查范围（js/ 仅作源码存档，
  │     │       规范检查不涉及 JS 逻辑，不必 Read）
  │     │       （方法论见 check-method.md「网页采集产物」节；CDN/跨域 CSS 已全部落盘，
  │     │         无需追链、不标"外部样式无法确认"，仅下载失败的表标 warning）
  │     │    c. Read check-method.md → 规范一律先 --scan-spec 粗筛拿候选行
  │     │       → 按需片段精读（🔴 禁止整读规范文件）→ 两遍法检查
  │     │       → issues 写入数据文件递交：--work-dir 原样透传采集 stdout 的「工作目录」
  │     │         （报告与采集文件同目录；sourceFile 写原 URL，
  │     │           issues[].file 写采集目录下文件的绝对路径）
  │     │    d. 🔴 跳过阶段 4 询问（网页模式只检查不修复——落盘副本的修复对线上无意义）
  │     │       → 汇报问题统计 + 报告绝对路径，流程结束
  │     │       （用户仍要求修复时，不尝试修复采集落盘文件，明确提示：
  │     │         "网页无源文件，无法修复；请提供该网页的前端工程/源码路径，
  │     │           提供后将按本地模式重新做检查与修复"）
  │     │
  │     └── 【本地模式】（检查 + 修复）
  │          Read 样式载体（引用链追本地 CSS；排除 node_modules/dist/build 等；
  │          外部 CSS 不读，检查时标 warning）
  │          规范一律先 --scan-spec 粗筛拿候选行 → 按需片段精读（🔴 禁止整读规范文件）
  │          （🔴 规范库混有示例代码、生成指南、开发教程等非规则内容时一律忽略；
  │            规则条目含数值类与定性类——设计风格、规整美感等抽象描述也要按
  │            check-method「定性规则检查」分解为可观察信号检查并给出具体修复意见）
  │          → issues 写入数据文件递交（🔴 0 问题也递交——尽力留痕；递交失败不阻塞，
  │            照常汇报检查结果）
  ├── 4. 询问（🔴 硬性交互点，仅本地模式；网页模式在 3-d 已跳过）
  │        N=0 → 告知"前端实现符合设计规范，未发现问题" + 报告路径，结束
  │        N>0 → 询问是否在副本上修复：全部 / 只修 error / 自定义 / 不修
  │              （info 为提示级——多为"禁硬编码但值等价"的形式问题，不影响视觉，
  │                汇报时单独一句话带过，不与真实违规混排，默认不修复）
  │              （定性类 warning 正常参与修复——检查阶段 suggestion 已是
  │                "元素+属性+目标值"的可执行工单，修复照单执行即可）
  ├── 5. 修复（仅本地模式；Read fix-guide.md）
  │        生成副本（🔴 原件只读）→ 逐条修复（每条回读 specFiles/<specFile>
  │        核对 specQuote）→ 复查 → fix-result 写数据文件递交
  └── 6. 汇报（🔴 一律绝对路径）
           网页模式：问题统计 + 报告路径（无副本/修复统计）
           本地模式：原件未动 + 副本位置 + 修复统计 + 未通过/failed 条目说明
           （询问是否继续）+ 报告路径
```

## 命令详细参数

```bash
node <skill目录>/bin/design-checker.mjs --list-specs [--spec-server <url>]        # 领域清单（服务端优先，本地兜底）
node <skill目录>/bin/design-checker.mjs --sync-spec <领域key> [--spec-server <url>]  # 检查&更新；stdout 固定输出「来源: server|local」
node <skill目录>/bin/design-checker.mjs --scan-spec <领域key>                     # 粗筛，纯只读
node <skill目录>/bin/design-checker.mjs --collect-web <url>                       # 网页模式采集（仅检查，无修复）

# 检查递交（两步）：① Write 数据文件 ② 传路径执行
#   路径 = <skill目录>/report-data/report-data-<当前时间 YYYYMMDDHHmmss>.json（会话唯一，仅此目录合法）
#   --work-dir（网页模式必传）：--collect-web stdout 返回的「工作目录」原样透传，
#     报告与采集文件同目录；本地模式不传
node <skill目录>/bin/design-checker.mjs [--work-dir <采集工作目录>] <数据文件路径> [--out-dir <绝对目录>]
# 修复递交（仅本地模式）：数据文件同上；--work-dir 从检查 stdout 原样透传
node <skill目录>/bin/design-checker.mjs --fix --work-dir <检查工作目录> <数据文件路径> [--out-dir <绝对目录>]
```

- 🔴 AI 只允许写** report-data/ 下的递交数据 JSON**，报告/存档一律由脚本生成；递交成功后脚本自动删除数据文件（失败保留原地，修正后重传）
- 🔴 禁止写 submit-check.js 之类的辅助脚本；禁止自己 Write 报告 md/存档 JSON
- **报告只是留痕日志，不影响检查/修复结果**：递交反复失败（重试 2 次）→ 跳过留痕，用会话内已有的结果照常向用户完整汇报（问题清单/修复统计 AI 手里本来就有），附一句失败原因
- `--work-dir` = 检查 stdout 返回的「工作目录」，**原样透传**
- `--out-dir` 仅当用户指定过报告保存目录时追加，整理成绝对目录（`~/` 与相对路径脚本会兜底展开）；未指定时报告落 `~/.octo-uxlint/design-check/`（7 天自动过期），用户指定目录不过期
- stdout 输出的路径均为绝对路径，汇报时原样告知

**串联规则**：`--list-specs` 清单「领域 key」→ `--sync-spec`；`--scan-spec` 候选行清单 → 检查依据 + specQuote 来源（按行号片段精读）；`--collect-web` stdout「工作目录」→ 检查递交 `--work-dir`（网页模式）；检查 stdout「工作目录」→ 修复 `--work-dir`（本地模式）。领域清单与规范内容一律经脚本获取，**AI 不直接 curl 服务端**。

## 🔴 失败处理

- **失败即止步**：命令报错（非零退出码 / stderr 有 `✗`）→ 停止流程，不假装成功
- **重试上限 2 次**（含首次共 3 次），耗尽后向用户报告，让用户决定下一步
- 服务不可达时 `--list-specs` / `--sync-spec` 已由脚本自动退回本地（stdout 标注来源），继续流程即可；本地无领域 → 报告用户，**不要自建规范目录**
- 递交失败 → 读 stderr（JSON 语法错定位行号原文 / 字段缺失一次列全），修正数据文件后重传；重试 2 次仍失败 → **跳过留痕**（检查/修复结果不受影响），照常向用户完整汇报 + 附失败原因
- ❌ 禁止：改 `bin/`、`lib/`、文档等任何源码；用空/假数据继续；自己写产物文件代替脚本；静默吞错

## 决策检查清单

- [ ] 先跑了 `--list-specs` 确认领域 key？（不能凭记忆指定）
- [ ] 读取规范前跑了 `--sync-spec`？
- [ ] 检查目标是网页 URL 时：用户意图确为规范检查（非纯采集诉求）？采集用的是本 skill 的 `--collect-web` 且在主线内执行（没有调其他工具）？检查递交透传了 `--work-dir`？没有进入修复阶段？
- [ ] 先 `--scan-spec` 粗筛、按候选行片段精读？（禁止整读规范文件）
- [ ] 0 问题时仍递交了检查数据？（递交失败时已降级：跳过留痕、照常汇报）
- [ ] 本地模式修复前询问了用户？生成了副本、原件未动？
- [ ] 每条修复回读了 specFiles/<specFile> 核对 specQuote？
- [ ] `--work-dir` 从对应 stdout 原样透传？（网页模式 = 采集工作目录；本地模式 = 检查工作目录）
- [ ] 汇报路径全部为绝对路径？
